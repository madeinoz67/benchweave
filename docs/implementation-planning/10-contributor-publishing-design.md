## 1. Problem, restated from code

The registry machinery exists and is strict; the path between "finished plugin" and "signed, discoverable, managed release" does not. From the tree at the evidence baseline:

- **Admission is owner-side and manual.** `src/benchweave/registry/admission.py:401` `admit` runs the five-step normative sequence (lifecycle gate with persisted high-water, limits, verified extraction, canonical lock, admission record); `src/benchweave/registry/admission.py:147` `_gate_lifecycle` refuses `revoked`/`yanked`/`stale_sequence` before any write. The gateway's only wired session is the fixture catalogue: `src/benchweave/interfaces/bootstrap.py:283` `build_registry_session` constructs one signed `origin-main` over `fixtures/registry` routing only the `benchweave` namespace (`REGISTRY_NAMESPACES`), and the admin act dispatches through it (`src/benchweave/interfaces/operations.py:1309` `_apply_package_admission`). Nothing packages a third-party submission; nothing records a review.
- **The SDK stops at the plugin boundary.** At pin `e948fd5` the CLI has exactly six subcommands (`new`, `check`, `inventory`, `check-ui`, `check-preset`, `sync-standards` — `src/benchweave_sdk/cli.py`), and `src/benchweave_sdk/packaging.py` carries only `inventory`/`verify_inventory` (file-inventory helpers). No packaging of a submission artefact set, no submit path. (Denominator: the pinned SDK tree's `cli.py` command registrations.)
- **The dev loop is unsigned by design.** `scripts/registry/publish_dev.py:141` `publish` deterministically emits `manifest.json`/`status.json`/`payload.zip` under a `dev-local` origin with no signatures — the honest dev posture, and the proof that keyless deterministic builders already exist (`scripts/registry/registry_common.py`). The signed builder is `scripts/registry/build_fixtures.py` (CI materialises fixture keys from repo secrets — fixture keys, not lane keys).
- **Discovery is a paragraph, not a catalogue.** `website/index.html:316` honestly states "the registry service and a device-install command do not exist"; the site's five panels carry no plugin surface. Version stamps on the site are already machine-derived (`scripts/assemble_docs_site.py:314` `website_stamp_map`, pinned by `tests/contract/test_website_stamps.py` — CON-13) — the discipline a catalogue must extend, not re-invent.
- **Review outcomes live in memory and PR threads.** The written human review checklist exists — `docs/device-developer-guide.md:574` §12 ("Human review and acceptance", eight verification bullets) — but nothing records an outcome against it durably. The manifest schema today has no review carrier: `standards/registry/0.1.1/release-manifest.schema.json` is `additionalProperties: false` throughout with `manifest_version` a `const` `"0.1.1"`.
- **Admission refuses only the four-name mutable set.** `src/benchweave/registry/manifests.py:37` `_MUTABLE_REVISIONS = frozenset({"main", "master", "HEAD", "latest"})` — CR-36's premise verified: a moving tag like `v1` passes gateway admission today; publish-time must be stricter.
- **A published yank cannot reach a running gateway.** `src/benchweave/interfaces/device_closures.py:132` `commissioned_device_closure` re-reads served manifests through the origin sources and digest-verifies them against the admitted lock — it reads no status document (M6, confirmed by both refute lanes; the PRD §5(l) audit).
- **The platform detection floor is absent.** Verified this session at the evidence baseline: no `.github/dependabot.yml` and no code-scanning configuration in the gateway repository; the SDK at pin carries workflows `ci`/`docs`/`publish` and neither file either (CR-59's own baseline-absence claim, re-verified).

The ADC-class friction (the PRD's §1.2 evidence: a real third-party implementation plugin restamped twice by hand because admission is manual) is the forcing function; the DPS-150 in-tree plugin (`plugins/fnirsi/dps150`, same class — a real instrument implementation) is this design's measurable control, per Q5's dogfooding ruling.

## 2. The hybrid home, resolved (PRD increment 4 collapsed)

Q1 ruled hybrid. This record resolves the home question into the slice map as follows — explicitly, because the PRD's increment list was written before the ruling:

- **What exists before the standalone registry repository is created:** nothing lane-owned. No records, no catalogue, no submission tooling exist anywhere today (verified in §1), so there is nothing to migrate *from*. Creating the home first is strictly cheaper than building records in-tree and migrating them: an in-tree `records/` start would put third-party submission traffic on the gateway repository (the wrong traffic shape §5(k) rejected), duplicate every CI guard at migration time, and break S3's "recoverable from the repository of record alone" mid-lane when the repository of record changed under shipped records.
- **What the creation slice (slice 1) builds:** the registry repository skeleton — `records/` tree and its schema, the reserved-namespace and lane-rules files, the records-validity + admission-replay CI, the CR-59 platform baseline, the CR-61 records-branch ruleset, and the dogfooded first submission (Q5).
- **What migrates in the conditional migration slice:** nothing. PRD increment 4 is **satisfied vacuously** — the design creates the repository of record before the first record exists. The only history that could be "migrated" is the DPS-150's two historical hand-restamps, which have no structured review records; back-filling them as records would fabricate evidence. **Honest negative: history stays in git history and PR threads; the first structured record is the slice-1 dogfooding submission, and the catalogue entry cites that release.** One committed mirror does move gateway-side later (the generated index copy, slice 2) — a derived copy whose authority stays with the registry repository, the CON-12 `sdk_compatibility` mirror pattern, not a migration.

*Direction (non-binding)* registry repository layout (name and exact dirs refinable; the served tree MUST satisfy `LocalDirectorySource`'s `<root>/<package_id>/<version>/` contract so a clone is a resolvable origin):

```
benchweave-registry/
  records/                      # committed review + lifecycle + sharing records (canonical JSON, schema-validated)
    submissions/<publisher>/<plugin>/<version>/review-<n>.json
    lifecycle/<package-id>/<version>/<seq>-<op>.json     # publish | yank | advisory | unlist | takedown | transfer
    publishers.json             # vetted publisher identities + namespace assignments
  lane-rules.json               # reserved prefixes, similarity-rule params, transport tier rule placeholder (Q15)
  review-checklist.md           # the versioned owner checklist (CR-8), machine-citable row ids
  releases/<registry-id>/<package-id>/<version>/{manifest.json,manifest.sig,status.json,status.sig,payload.zip}
  index.json                    # GENERATED from records + releases — never hand-edited (CR-21)
  keys/main.pub.pem             # the public trust root (fingerprint listed — CR-40, slice 6)
  gateway-ref                   # the pinned gateway commit the admission replay runs at (Q10)
  .github/workflows/records.yml # validity gate + admission replay + index regen + cross-repo drift
  .github/workflows/codeql.yml, dependabot.yml   # CR-59 baseline
```

CR-34's falsifier holds by construction: a clean-room clone regenerates `index.json` (the generator is committed in the repository and runs offline over `records/` + `releases/`) and verifies every published release's digests (the served tree plus the public root are in the clone; the admission replay is exactly this check run with the gateway's own code).

**Repo-hygiene boundary:** the registry repository is public like the other two — NFR-1 applies to every record, catalogue row and example; publisher identities are GitHub identities plus a publisher name (NFR-7); invented names in every fixture.

## 3. The mechanism, end to end

### 3.1 Submission artefacts and packaging (CR-1..CR-4, CR-16, CR-45/49/50 gates)

A new SDK module (Direction: `src/benchweave_sdk/publishing.py`) and two CLI subcommands (Direction: `benchweave-sdk package`, `benchweave-sdk submit`):

- **`package`** builds the single generated artefact set (CR-1): release manifest, descriptor(s), adapter source reference, conformance evidence, licence/provenance declaration — deterministically (canonical JSON, sorted fixed-timestamp ZIP members — the `publish_dev.py`/`registry_common.py` discipline, re-implemented SDK-side). The manifest is generated, never typed: every pin derives from the plugin's own tree (descriptor pin, plugin lock where #203 has landed, payload inventory digests computed from bytes). A missing component refuses naming the component (CR-1's falsifier). The builder's byte discipline is pinned to the gateway's fixture builder by a **builder-parity test** (gateway-side, the `tests/sdk/` cross-repo pattern of `test_adapter_agreement.py`): the SDK-built manifest for the DPS-150 inputs equals the fixture-builder-built manifest for identical inputs; diverge the builder, the parity test fails. This keeps the two repos decoupled (the SDK never imports gateway code — REG-4's read-not-import posture) while pinning agreement.
- **Entry gates as packaging refusals** (the PRD increment-1 §5(l) criteria — each a stable machine prefix, each RED-provable on a mutant fixture):
  - `dev_lineage_refused` (CR-35): any dependency or root whose `registry_id` is dev-prefixed (`dev-*`, the `dev-local` convention of `publish_dev.py`) refuses at packaging; the published index can never contain a dev-prefixed registry id because the gate runs before a submission can complete.
  - `source_ref_mutable` (CR-36): the source linkage must be a commit digest (40-hex SHA-1 or 64-hex SHA-256, resolved locally before packaging completes); anything else — branch, tag, any moving name — refuses. This is deliberately stricter than admission's four-name denylist (`manifests.py:37`), as CR-36 requires.
  - `capability_declaration_absent` (CR-45): no packaging without a capability declaration (network egress / subprocess or native-library use / filesystem writes beyond evidence retention — a closed three-way enumeration plus explicit `none`, so absence is unrepresentable in a finished package). Enforcement is deploy-policy only (Q13); the declaration is discovery input.
  - `transport_triples_absent` (CR-49): a descriptor declaring a transport provider must publish its admitted contract triples or refuse. The tier rule itself is recorded in `lane-rules.json` now (Q15) with its activation trigger naming #167.
  - `firmware_provenance_absent` (CR-50): a payload bundling `firmware/` without vendor attestation pinned against a vendor manifest refuses.
- **`submit`** prepares the git-native channel (CR-6): writes the artefact set into a working copy of the registry repository's submission layout, creates the branch, and opens the PR via `gh` when present, else prints the compare URL. No service is required at any point — the cycle completes with git and review tooling alone (CR-6's falsifier). Namespace checks run at packaging time against the clone's `records/publishers.json` + `lane-rules.json`: `namespace_collision`, `namespace_reserved` (the Q3 reservation list: `benchweave`, `otdp`, `dev-`, in-tree fixture names — written and committed before the first submission, CR-16), and `namespace_lookalike` flag-or-refuse under the committed similarity rule (CR-39; test vectors committed with the rule).

### 3.2 The review block inside the signed manifest (Q2) — and the registry 0.1.2 PATCH bump it needs

The manifest schema is `additionalProperties: false` with `manifest_version` a const — review fields cannot ride inside the manifest without a corpus change. The design:

- **Registry standard 0.1.2 (PATCH, additive-optional, copy-never-move from 0.1.1).** The new version's `release-manifest.schema.json` changes exactly two things: `manifest_version` becomes an **enum `["0.1.1", "0.1.2"]`**, and an optional `review` block (`checklist_id`, `checklist_version`, `reviewer_id`, `outcome` enum, `record_sha256`) is admitted, **required iff `manifest_version == "0.1.2"`** under an `if/then` — the same conditional pattern the schema already uses for `kind` (the profile/implementation blocks). The enum arm is what keeps CR-13 intact: every existing 0.1.1 manifest (the entire fixture catalogue) validates byte-identically under the new active schema, so no existing release's admission outcome moves.
- **Optional in schema, required by the lane.** The gateway never consults `review` — admission validates structure and verifies the four pillars (origin signature, sequence high-water, lifecycle, digests — CR-13's own enumeration) and nothing else. The requirement to carry review lives in the registry repository's CI: a publish record whose manifest lacks the review block, or whose review block disagrees with the committed review record, refuses. This is the reconciliation of Q2 (fields inside the signed manifest) with CR-13 (admission unchanged): the corpus schema admits the fields; the lane enforces them; admission stays indifferent.
- **The digest chain that closes the review-to-sign swap.** The contributor's submission manifest (no review block) has digest `D_sub`. The owner's review record pins `D_sub`, the closure digest covered (CR-38), the reviewer identity, the outcome, and the cited platform findings (CR-60). The signing step re-derives the manifest **from the submission's pinned inputs** — recomputing payload digests from the CR-36-pinned source revision, never trusting the submitted manifest bytes — inserts the review block carrying `record_sha256` (the review record's digest), and signs. Any post-review change to payload, source, or pins changes `D_sub`, breaks the review record's pin, and CI refuses (CR-11/CR-14 falsifiers). The one origin signature attests release and review together (Q2 — no countersignature, no second key).
- **Version declaration (CR-18/CR-19, Q11):** written verbatim into the existing `compatibility` block (`otdp_versions`/`stg_versions` — the schema fields that exist today), derived from the plugin's own pins; semantics are #203's entirely. If #203's carrier ruling moves anything, this lane's writer follows and a second mechanism is a defect (CR-18's own falsifier).

**Signing tooling is maintainer-side and keyless SDK stays keyless.** The sign command lives in the gateway repository (Direction: `scripts/registry/sign_release.py`, beside `build_fixtures.py`, reusing its signing stack) — the SDK's keyless property is a pinned posture (`publish_dev.py`'s fresh-interpreter test) and stays that way. **The origin signing key never enters any CI** — unlike fixture keys (repo secrets, obligation 5), the lane's real key is maintainer-custodied (CR-12); CI verifies with the committed public root only. CI-as-signing-oracle is thereby structurally absent, not policy-absent.

### 3.3 Review workflow and records (CR-8..CR-11, CR-54, CR-60, CR-61)

- **The versioned owner checklist** (CR-8) extends `docs/device-developer-guide.md:574` §12's eight bullets with the publishing rows: closure-diff coverage (CR-38), capability declaration display (CR-45), transport triples (CR-49), firmware provenance (CR-50), execution-model disclosure (CR-52), platform findings consulted (CR-60), publisher-repo protections declared-not-verified (Q21). It lives in the registry repository with machine-citable row ids so records can name rows and CI can check citations.
- **Records schema and validity gate (CR-9/CR-10/CR-56).** A lane-owned JSON Schema over canonical JSON records. CI refuses: a changes-requested record citing no failed requirement or checklist row (CR-10); a record naming no platform findings at the pinned revision (CR-60 — same check family); a record without a `kind` tag (CR-56; kinds `admitted-release` and `in-tree-fixture` exist from slice 1, `community-shared` from slice 5); a publish record whose closure diff versus the prior release of the same package is absent, or whose sign-off names a different closure digest than the one published (CR-38).
- **Re-review on revision change (CR-11).** The signed manifest's review block pins the review record; the review record pins `D_sub`; `D_sub` pins the source revision and payload digests. A revision change anywhere in that chain is a digest mismatch at CI — structurally, not by sweep.
- **Records-branch ruleset (CR-61).** The registry repository's default branch enforces required approvals, the records-validity and admission-replay checks as required status checks, linear history, no force pushes, no direct pushes.
- **Admission replay (Q10).** The registry repository's CI checks out the gateway repository at the committed `gateway-ref` pin, runs the real `resolve` → `admit` over the submission's served tree with the committed public root, and asserts success — the `tests/integration/test_registry_reuse.py` construction (fresh roots, fresh high-water, `LocalDirectorySource` over the served tree). This is the authoritative CR-13 falsifier check: an accepted release admits through unmodified admission, executed by the gateway's own code at a pinned ref. A drift job warns when gateway `main` advances past the pin (the CON-12 staleness pattern); the pin advances deliberately per train.
- **Accountability on demand (CR-54).** The chain — publisher identity, reviewer identity, signed approval, closure digest, capability declaration — is exactly the records tree plus the signed manifest; a single verify command (see 3.5) emits it from a clean clone.

### 3.4 Catalogue and search on the public website (CR-19..CR-26, CR-37, CR-56..CR-58)

- **One generated index, two committed copies, one authority (Q7, CR-21).** `index.json` is generated in the registry repository from `records/` + `releases/` (rows: coordinates, kind, publisher, immutable release id, manifest digest + signature presence, compatibility verbatim from the manifest — CR-19, licence, evidence links, maintenance status, advisories, capabilities, transport triples, source ref, unverified markers per CR-37). The gateway repository holds a **committed mirror** (Direction: `website/plugins-index.json`) synced by a registry-repo workflow that opens a PR on records changes — the `sdk_compatibility` mirror pattern: a derived copy whose authority stays with the generator. A runtime fetch or an unpinned build-time checkout is rejected because CR-21's falsifier ("a records change without catalogue regeneration fails CI") needs a regeneration step to fail, and CON-13's committed-state purity binds the site render.
- **Two-sided drift gate.** Registry side: CI regenerates the index and refuses a records change whose regeneration differs from the gateway mirror's `main` bytes (raw read — CI has network; the SITE never does). Gateway side: the panel render test regenerates the panel markup from the committed mirror and byte-compares — a hand-edited mirror row or hand-edited panel row is refused (the `test_website_stamps.py` tamper-arm class, extended).
- **The Plugins panel (CR-20/22/23).** A sixth panel (or page set) rendering at assembly from the committed mirror; default view = accepted+signed releases only, every row carrying the seven registry-contract fields or an explicit "none"; in-flight submissions never render (CR-22); the panel states what is built and what is not — the honesty sentence at `website/index.html:316` is updated the moment a catalogue exists, and no "registry service" claim appears while none exists (CR-23). CON-13's class-11 literal ban covers the new panel (no three-component version literals — versions render from the index).
- **Static search (CR-24/25/26).** Client-side filtering over the same index (name, publisher, device class/capability, standard version, status, kind — CR-58). No service: the control is a clean static deploy serving working search.

### 3.5 Management surfaces (CR-15..CR-17, CR-27..CR-33, Q3/Q9)

CLI/records-first (CR-30); every command runs against a clone of the registry repository. Direction: the SDK CLI gains a `registry` family — `queue`, `status`, `publish` (the sign+record step of 3.2), `yank`, `advise`, `unlist`, `transfer`, `takedown` — while the sign step itself is the gateway-side script (3.2); the split is a fork (F2). Queue state (CR-27) derives from open PRs (the repository's review surface — PRs are repository state) plus committed records (the durable outcomes, Q4); the PRD's "derivable from the repository of record alone" is read as the GitHub repository including its PRs, and this reading is stated here so it is checkable. Lifecycle ops each write a record carrying actor, reason, timestamp (CR-28); yank reuses the existing status lifecycle (`revoked`/`yanked` in `standards/registry/0.1.1/release-status.schema.json`, enforced at `admission.py:147`) — the catalogue reflects it within one records refresh (the sync-PR window, named as S5's bound) and stock gateways already enforce it at admission (CR-29). Contributor status is queryable by publisher from records (CR-31); withdrawal pre-acceptance is a record, withdrawal after signing means advisory or unlist — **no operation erases a signed release from history** (CR-32; git history is the floor). Transfer is re-vetting: both-party consent + coordinator approval records, receiver held to the CR-35/39 bar, silent reassignment unrepresentable (CR-17, Q9). The consumer surface is read-only (CR-33): adoption guidance names where the release lives (the registry repository), how to verify it (the verify command, the public root), and that commissioning remains local (REG-3: publication never authorizes control).

### 3.6 Response reach (CR-53, Q14, NFR-S2/S3) — the one gateway change

`commissioned_device_closure` (`src/benchweave/interfaces/device_closures.py:132`) gains a **status consult** beside its manifest re-read: for each closure release, read the served `status.json` through the origin source, verify it against the session's trust root, and consult lifecycle — **without** the resolver's strictly-advancing fence (the module's own docstring explains why the resolver cannot be reused here; the consult is read-only, advances no high-water, and is a consult, not an admission). A `revoked`/`yanked`/advised release at run-build refuses with a machine-prefixed `closure_status_*` error or delivers a recorded operator advisory (the non-run-build path: the recorded operator delivery of Q14). The read is cached with a committed staleness bound (NFR-S3's direction); a fresh-cache run-build performs zero status reads (monkeypatched-socket control), and a view older than the bound re-reads. NFR-S2's statement names its denominator: gateways reachable at next run-build get the bound; gateways offline since publication are covered by the recorded operator delivery half. This closes M6 (yank-without-reach) at the only place it can be closed without touching admission — and admission is untouched: a revoked release was already refused at admit time by `_gate_lifecycle`; this extends the same enforcement to closures admitted before the revocation.

### 3.7 Author-sharing (§5(m), Q20)

`community-shared` records: any vetted publisher may share a standalone plugin as a records entry carrying publisher identity, a pinned immutable source ref, licence, declared compatibility, and the explicit unverified marker (CR-57); open-listing, anyone may request a takedown, reason recorded, no response SLA promised (Q20); unlisting is a recorded admin op touching no admitted release (CR-28 class). Shared entries never appear in the default available view and are never rendered as admitted (CR-22 holds); kind is a search dimension so shared plugins neither drown out nor masquerade as admitted ones (CR-58). The §5(l) threat classes apply in full — the kind tag is differentiation and honesty, not trust reduction; CR-46's isolation posture applies to shared plugins by default (cross-referenced, enforced slice 6).

### 3.8 Execution posture and trust hardening (CR-40/41/43/44/46/47/48, Q16/Q17)

- **Loader parity (CR-43):** `src/benchweave/registry/activation.py:121` `load_plugin` (the legacy leg — verified bytes, no import fence) refuses packages whose `registry_id` is not dev-prefixed (`legacy_leg_refuses_published`); the documented dev loop (`publish_dev.py` → dev origin → `load_plugin`, `docs/device-developer-guide.md:491`) is unaffected — the refusal is lineage-keyed, not a blanket break. Published packages load only through `load_otdp_plugin` (bundle import fence + exec-time re-verification, `src/benchweave/registry/otdp_loading.py`).
- **Sim-lane separation (CR-44):** a guard test fails if `_load_sim_plugin` (bare importlib, zero checks) can load anything outside the fixed in-tree fixture map.
- **Isolated evaluation posture (CR-46):** the documented trial flow for untrusted/new publishers refuses to start without the isolation mechanism (Direction: a trial runner that verifies the deployed unit's hardening markers — unprivileged user, read-only FS, no new W+X — and refuses naming what is missing). Interim per Q16: the systemd unit plus publishing accountability; process/interpreter isolation, the evidence MAC and the plugin-independent safe state stay recorded residuals (§5, REG-5's disclosure clause).
- **Trust root and keys (CR-40/41):** a signed fingerprint list published with the index; provisioning checks the installed root's fingerprint against it before trusting (today `bootstrap.py:283` loads whatever PEM sits at the keys path, unchecked — the M2 gap). Key rotation/revocation rides the same channel, distinct from per-release yank. The production-mode structural refusal of dev-unsigned origins (Q17) lands here, tied to this work.
- **Egress decision (CR-47, Q18):** the permissions record records the decision — operator deploy config owns the allowlist once legitimate endpoints are nameable; until then the accepted risk is recorded explicitly covering plugin-originated outbound connections. **Protective-path responsiveness (CR-48):** a measurement harness (dispatch/verify latency under load during qualification); an adapter blocking beyond budget records a failure, not a pass; instrument-plugin qualification records carry the measured figure. Slice 1's records schema carries the field as optional with the dogfooded entry disclosing "not yet mechanized" — the requirement becomes binding when the harness lands.

## 4. Slice map (dependency order)

### Slice 1 — builds the publishing path and the records home (PRD increment 1, plus the home creation)

Three-repo landing in the AGENTS.md order: registry repository (creation: skeleton, records schema, checklist v1, lane rules, CI, CR-59 baseline, CR-61 ruleset) + SDK PR (`publishing.py`, `package`/`submit`, entry gates) + gateway PR (registry 0.1.2 corpus bump via repin + specification prose for the review block + validation-report rerun (obligation 13) + `sign_release.py` + builder-parity test + publishing docs (S2) + the CR-51/52/55 documentation-boundary records) + submodule pointer if the SDK lock moves (the vendored registry 0.1.2 schema syncs SDK-side through the ordinary `sync-standards` flow, obligation 6). Closes with the dogfooded DPS-150 submission (Q5): packaged, submitted, reviewed against checklist v1, signed, published, replayed.

**Precedents extended:** `publish_dev.py`/`registry_common.py` (deterministic keyless builders — re-implemented SDK-side with parity pinned); `build_fixtures.py` (the signed builder, extended by `sign_release.py`); `tests/integration/test_registry_reuse.py` (the replay harness); `docs/device-developer-guide.md:574` §12 (the checklist base); `test_website_stamps.py` (tamper-arm discipline, consumed in slice 2); the fixture mutant style of `tests/contract/test_registry_*.py` (7 files) for the entry-gate battery.

## 7. Top risks — and what an adversary attacks first

The PRD's M1..M7 classes are the map; against THIS design the first attacks are:

1. **Review rubber-stamping (M1's process face).** Machine evidence is advisory; an adversary's cheapest win is a reviewer who signs anything. Controls: the identified-reviewer rule (CR-8's outcome references checklist AND machine evidence), CR-38's closure digest in the sign-off, CR-60's findings-or-invalid records, CR-61's required approvals. Residual — honest, per (l.6): a correctly-signed malicious release has no technical backstop; publish-time review owns that residual, and Q12 holds the line rather than pretending admission can close it.
2. **The review-to-sign swap.** Payload or source changed between review and signature. Structural defense: the digest chain (§3.2) — the signer re-derives from pinned inputs; any change breaks `D_sub` and CI refuses. Falsifier: a mutant submission with post-review source motion must refuse, not warn.
3. **Records or index forgery/drift.** A forged lifecycle record, a hand-edited index, a stale mirror. Controls: CR-61's ruleset (no direct pushes), the two-sided drift gates, canonical schema-validated bytes, and CR-55's posture — gateway-local state is never provenance. The sync-PR window is S5's bound and a red drift gate is the honest intermediate (degrade loudly).
4. **CI as signing oracle.** If the origin key ever reaches CI, every "verified" chain launders CI compromise. Structural: the lane key is maintainer-custodied and CI verifies with public halves only (§3.2) — the fixture-keys-from-secrets pattern is explicitly NOT followed for the lane key. Falsifier: a workflow-file test refusing any secret named like the origin key in signing contexts (cheap, worth it).
5. **Namespace typosquat / confusion (M1 variant).** The similarity rule flags-or-refuses lookalikes; residual: the rule is heuristic and its vectors are committed — a novel confusable passes to human review, which is where CR-39's "verified publisher behind the namespace" display puts it.
6. **Local-state re-pointing (M3) — unchanged, disclosed.** This lane neither widens nor closes it; CR-55's decision record (slice 6's F-family lands the record; slice 1's docs carry the boundary statement per the PRD's "cheap documentation requirements ride the first increment") names the exact local-writer capabilities.
7. **Measurement-truth laundering (M5).** A realistic fabricated reading passes every check; CR-51's boundary statement ships slice 1 exactly so no catalogue row or record implies digest verification establishes measurement truth (NFR-S1 audit arms in slices 1/2/5).
8. **The enum-arm schema change silently breaking old manifests.** A7's control runs the entire fixture catalogue through admission against the new active schema; the KILL direction is any outcome moving. This is the one place slice 1 could damage CR-13 by accident, so it is pinned hardest.

**Q19 blocker, restated:** one threat-catalogue entry reached both refute lanes truncated and was never verdicted. Per the ruling it blocks treating §5(l) complete — this record's §7 and slices 4–6 acceptance carry that obligation (D8). The three status gates it references (expiry, future-time tolerance, sequence high-water) are verified real machinery (PRD §7.19); the design does not assume the entry's content.
