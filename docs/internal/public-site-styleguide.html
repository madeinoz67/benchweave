BenchWeave design system

Tokens and components for benchweave.dev — the landing site, versioned standards pages, user guides, and the SDK pointer. Independent from the internal application UI style guide by design: the app is an instrument operator's console; this is the front door for engineers evaluating and building on BenchWeave. Same product, deliberately different register.

Principles

Four rules everything below should answer to.

Precise over persuasive

This is infrastructure for people who build test procedures for a living. State what BenchWeave does and where it stands. No hype, no unearned superlatives.

One bespoke element per page

Spend the design's boldness on the thing that's actually specific to BenchWeave — the connection diagram, a real spec table. Everything around it stays quiet.

Dark-first, light at parity

The audience works in terminals and scope screens. Dark is the default register; light mode gets the same contrast and hierarchy, not an afterthought.

Every label is real

Contract names, version numbers, and status words come from the actual repo. If it's not true yet, it says "planned," not marketing copy.

Ambient instrument background

Hero-only texture: real oscilloscope front panels and standalone glowing traces, tilted in genuine 3D (not flat rotation) and rendered with a soft phosphor glow. Live, faint, and never the thing your eye lands on first — the hero diagram stays that.

Shown here at higher opacity so the treatment reads clearly. In production it sits at 0.18–0.22 — texture, not content.

Recipe

/* tilt: perspective on the parent, rotateY/rotateX/rotate on the element */ .hero-bg-scopes { position: absolute; inset: 0; z-index: -1; pointer-events: none; overflow: hidden; perspective: 900px; } .scope-panel { transform: rotateY(-27deg) rotateX(7deg) rotate(-3deg); opacity: 0.22; } /* glow: layered drop-shadow, not a blur filter on a rect */ .scope-trace { stroke: var(--amber); stroke-width: 2; filter: drop-shadow(0 0 4px var(--amber)) drop-shadow(0 0 10px var(--amber)); }

Gotcha worth keeping: z-index: -1 only tucks an element behind its siblings if the parent itself establishes a stacking context. position: relative alone does not — it needs an explicit z-index (e.g. 0) on that parent too, or the layer renders behind the page background and disappears entirely.

Usage

  • Hero sections only — never behind body copy or docs content, where it would fight legibility.
  • 2–4 elements per hero, spread on a diagonal with real gaps between them. Corner-clustering reads as clutter, not atmosphere.
  • Alternate amber and blue glow so no two neighboring elements share a color.
  • Keep opacity in the 0.15–0.24 band. Below that it's invisible (see the gotcha above); above it, it competes with the hero diagram.
  • Mix panel treatments (bezel + screen + knobs) with bare traces (no bezel) for rhythm — don't repeat one asset four times.

Iconography

Use Lucide exclusively — it's what Great Docs ships (1,900+ icons, theme-aware via currentColor), so nav and inline icons match automatically between the marketing site and the docs site with zero extra assets. Stroke width 2, 20px in nav contexts, 1em inline.

Logo

One mark, built from the same grammar as the hero diagram: the gateway's hexagon, and the amber-under/blue-over wire-hop that stands for "weave" everywhere else on the site. Not a separate decoration — the same visual idea, just small enough for a nav bar.

Reads the same way at both scales the site needs: as a favicon glyph (the hexagon silhouette alone) and as a nav-bar mark (hexagon + weave visible). Below 16px, drop the hop detail and render the crossing as a plain X — it'll still read as an interlace.

Usage

  • Minimum size: 16px (favicon). Below that, use the hexagon outline alone.
  • Clearspace: half the hexagon's width on every side — don't crowd it against the wordmark or a rule line.
  • Colors are fixed (Trace Amber hexagon + amber/blue weave) in both themes — the mark does not invert or go monochrome.
  • Don't recolor the two strands to match a page's accent, don't stretch the hexagon, don't add a drop shadow.

Export as assets/logo.svg for both themes (the amber/blue pairing already holds contrast on light and dark) — no separate logo-dark.svg needed unless the hexagon stroke itself needs to shift for contrast. Great Docs auto-generates favicons from this file; see the mapping below.

Voice & tone

Write like the README, not like a landing page.

  • Active voice, present tense: "Connects instruments through reusable plugins," not "Instruments can be connected."
  • State status honestly. "Architecture baseline and Python scaffold" is the actual status line — use it instead of inventing a more finished-sounding one.
  • Name real things: OTDP, the registry, the five steps — not "our platform" or "powerful integrations."
  • No exclamation points, no "seamless," no "just three commands" unless it's literally three commands.

Accessibility floor

  • Body text meets 4.5:1 contrast in both themes; the light-mode amber/blue text shades exist specifically to hold this on white.
  • Every interactive element has a visible focus ring (inherit from :focus-visible, 2px, Signal Blue).
  • Respect prefers-reduced-motion — the one hero animation degrades to a static state.
